# The forecast on Home Compute (a Mac mini)

The worker image runs on this Mac through [Home Compute](https://github.com/sprintengine/home-compute)
and Bacalhau, on `deploy/local/jobs.toml`'s timetable, and publishes each run to the
R2 bucket. Visitors only ever read the bucket, so the site keeps serving the last
forecasts if the Mac is off; it just stops updating.

```text
launchd ─┬─ dev.sprintengine.home-compute-vm  starts the jobs' Colima VM at login and on a mount
         ├─ dev.sprintengine.bacalhau         bacalhau serve (orchestrator + compute), that VM's Docker
         └─ dev.sprintengine.home-compute     home-compute daemon: submits each job on its UTC slots,
                                              API on 127.0.0.1:4786 for the menu bar app
```

## Off since 18 October 2026: the hosted control plane schedules the jobs

Since 18 October 2026 the jobs are scheduled by Home Compute's hosted control plane
(`hc-core` and `hc-web` on Cloudflare). This Mac runs its pull agent
(`dev.homecompute.agent`, log `~/Library/Logs/home-compute/agent.log`), one run at a
time (`caps.maxRuns: 1` in `~/Library/Application Support/home-compute/config.json`,
and the machine's capacity on the plane). The agent pulls the released forecast image,
the `linux/arm64` entry of its manifest list, with the plane's `ghcr-read` vault
secret. The three launch agents above are stopped and **disabled**. Their plists stay
in `~/Library/LaunchAgents`, and `wingfoil-forecast:local` stays in their VM.

What the plane runs:

- Every job in `home-compute.json`, with the same slots, imported with the `wingfoil`
  preset. The jobs pin the release's manifest-list digest, with `registryAuth:
  vault:ghcr-read`.
- `prune` and the big downloads (the HARMONIE, ICON-EU, ECMWF and GFS families) require
  `site=home`, so only this Mac runs them.
- The rest prefer `mac-mini` and fall back to the cloud worker after 300 s.

A change to `deploy/local/jobs.toml` no longer takes effect by restarting a local
scheduler. Regenerate `home-compute.json`, then import it into the plane:
`home-compute cloud import deploy/home-compute/home-compute.json --preset wingfoil`
from the home-compute checkout. Edits made on the dashboard are kept unless you pass
`--force`.

### Switching back to the local scheduler

1. Pause the wingfoil jobs on the hosted plane, or at least `prune`. Never let `prune`
   run on both. Pausing the plane does not stop this Mac's agent; it just gets nothing
   to run.
2. Re-enable the launch agents, then start them:

   ```sh
   for label in dev.sprintengine.home-compute-vm dev.sprintengine.bacalhau dev.sprintengine.home-compute; do
     launchctl enable "gui/$(id -u)/$label"
   done
   deploy/home-compute/macmini.sh start    # the VM, Bacalhau, then the controller
   deploy/home-compute/macmini.sh status
   ```

   `start` bootstraps the plists, and launchd refuses a disabled label, so step 2
   needs the `enable` first. To use the released image instead of the local build,
   run `macmini.sh pull` (`:production`, multi-arch since `v2026.10.18-nightly.38`).
3. To return to the plane, reverse it: `macmini.sh stop`, `launchctl disable` the three
   labels, then resume the jobs on the plane.

## Files

| File | What it is |
| --- | --- |
| `home-compute.json` | Generated by `deploy/schedules.py` from `deploy/local/jobs.toml`. Edit the TOML, then rerun the script. |
| `.env` | Private (git-ignored): the image, the R2 bucket and key, `FORCE5_SIDECARS=0`, the API token. `setup` writes it from `r2.env`. |

| `../../../home-compute-vm/` | The jobs' own Colima VM, profile `home-compute`, beside the checkout (`HOME_COMPUTE_VM_DIR` moves it). Its disks grow there, on the checkout's drive, and outside the checkout so the image build never sends them as context. |

| `panel.py` | The app's JSON answers: service state, `.env` settings, the R2 check, token rotation, image freshness. |

## From the menu bar

Home Compute Bar (`../home-compute/macos`, `./build-app.sh --install`) runs this
script for you: its window sets up and starts the services, edits the R2 settings
and tests the bucket, rebuilds the image when the code has moved on, and edits the
timetable. A timetable edit is written to `deploy/local/jobs.toml` (comments kept)
and regenerated for Home Compute by `deploy/schedules.py --set`;
restart the scheduler to apply it, as for an `.env` change.

## Run it

Needs Colima, Node 22+, the Bacalhau CLI in `~/.local/bin` and a `../home-compute` checkout.

```sh
deploy/home-compute/macmini.sh setup     # image, .env, token, launch agents; starts nothing
deploy/home-compute/macmini.sh start     # both services; they also start at login from now on
deploy/home-compute/macmini.sh status    # each job: next slot, last outcome, run published
deploy/home-compute/macmini.sh run harmonie   # one job now
deploy/home-compute/macmini.sh logs
deploy/home-compute/macmini.sh stop
```

After changing the importer code, `macmini.sh image` rebuilds `wingfoil-forecast:local`;
the next submission uses it. No registry is involved: Bacalhau runs the local image.
Rebuild before restarting the scheduler on a timetable that passes the worker a flag
the old image lacks: the ECMWF job's `--ecmwf-cycle 00` (October 2026) fails at once
on an older image, with argparse's "unrecognized arguments", until it is rebuilt.

Colima's `home-compute` VM has to be running for any job to start. `start` starts it
if it is not, and `setup` writes a launch agent that starts it again at login, and
whenever a drive mounts, so a checkout on an external drive that comes up late still
gets its VM. `colima-autostart off` unloads that agent.

The VM is its own, not Colima's `default`, and lives in `home-compute-vm/` beside the
checkout rather than in `~/.colima`:
its image layers and job scratch grow on the checkout's drive, not the Mac's startup
disk. On 15 October 2026 the `default` VM's disk, on a nearly full 256 GB startup
disk, began failing every read with "input/output error", and every job queued for
its hour and failed. `colima` commands need `COLIMA_HOME=../home-compute-vm` (from the
checkout) and `-p home-compute` to see it.

## What a slot costs

Every forecast importer except tides and sea temperature first reads the run the
bucket already serves and exits at once if its source has nothing newer
(`readsPublishedRun` in `force5/ingest/registry.py`), so ECMWF's 10:20 retry after
its 08:20 slot has published, or a SWAN slot that finds the same day's run, costs a
listing, not an import.

Bacalhau is told the Colima VM's size, less half a GiB for Docker and the kernel,
and each job's memory is a hard ceiling (`RESOURCES` in `deploy/schedules.py`): 1 GB
for HARMONIE, ICON-EU, ECMWF and GFS-Wave, 512 MB for everything else. Every job asks
for one CPU, and Bacalhau is told it has one, so only one job runs at a time (below).

## One job at a time

Since 18 October 2026 the jobs never run side by side: two at once was more memory
than the owner wanted this Mac to give up for something meant to run in the
background. `macmini.sh setup` gives Bacalhau one CPU (`BACALHAU_DEFAULT_CPUS`), and
every job, the bucket sweep included, asks for a whole one, so a job whose slot
comes while another is running queues until it has finished (`test_schedules.py`
holds every enabled job to that). No run takes long: on 18 October the longest
was ICON-EU at 5½ minutes, HARMONIE 3½, GFS 4, and the hourly feeds about 30
seconds, so the slots that share a minute (sea temperature, the archive and SWAN
at :15) wait seconds, and nothing comes near the hour a job may queue. To let two
run at once again, in a 3 GiB VM: `BACALHAU_CPUS=2 deploy/home-compute/macmini.sh setup`.

## What a job uses

Every job's event now carries `resources`: its CPU seconds and the peak resident
memory of the worker and its adapter (docs/LIVE_FORECAST_PIPELINE.md, "Where a job's
time goes"), so the Home Compute log shows what each run really took. The ceilings
come from measuring each enabled job on 11 October 2026, on this Mac with the
repository's `.venv` and a scratch `FORCE5_WORK_DIR`, never with a bucket:

| Job | Ceiling | Peak, MB | CPU s | How it was measured |
| --- | --- | --- | --- | --- |
| `gfs-wave` | 1 GB | 360 | 2.5 | a live run, local output only |
| `gfs-weather` | 1 GB | 355 | 7 | a live 384 h run, local output only (22 October 2026) |
| `icon-eu` | 1 GB | 335 | 16 | 73 hourly frames decoded from cached GRIB (*) |
| `ecmwf` | 1 GB | 315 | 4 | the whole cached 2026100700 run, 85 frames |
| `harmonie` | 1 GB | 290 | 5 | 61 hourly frames from cached GRIB (*); two whole files downloaded at once peaked at 171 |
| `gfs` | 512 MB | 230 | 2 | a live run |
| `icon-eu-weather` | 512 MB | 225 | 13 | a cached run, 25 steps (three-hourly, as scheduled then; hourly since 24 October 2026 is 73 steps and not yet measured) |
| `verify` | 512 MB | 225 | 23 | a 30-day archive made from today's archived runs |
| `mi-swan` | 512 MB | 190 | 1 | a live run |
| `currents` | 512 MB | 240 | 4 | a live run (22 October 2026) |
| `blend` | 512 MB | 185 | 0.4 | the site's current runs, read over public HTTPS; includes Node |
| `forecast-archive` | 512 MB | 140 | 1.4 | archiving four new runs at once from that copy |
| `tides`, `sea-temperature`, `wind-obs` | 512 MB | 135 | 0.2-0.4 | live runs |
| `warnings` | 512 MB | 135 | 0.1 | the adapter's 62 MB measured natively on a live run (25 October 2026), plus the worker |
| `prune` (bucket sweep) | 512 MB | under 100 | - | the local sweep; the bucket listing adds little |

The peak is the worker with its S3 client (72 MB) plus the adapter's own peak, which
is what a container holds while the adapter runs; the worker's later upload phase
peaked lower (HARMONIE 172, ICON-EU 207 MB). (*) The cache held every third hour, so
the hours between were copies with their step rewritten: the same work as a real run
without downloading 785 MB of HARMONIE. macOS figures; the same adapters in the
`wingfoil-forecast:local` image under Colima read 10-25% lower (HARMONIE 180, ICON-EU
201, ECMWF 211 MB) and each finished under a 384 MB limit. Docker adds nothing to
speak of: a sea-temperature container peaked at 55 MB in its cgroup. A container's
cgroup also counts the page cache of the files it reads and writes, but Linux
reclaims that at the limit instead of killing the job (ECMWF under 384 MB met the
limit 248 times, with no OOM kill).

The ceilings are at least twice those peaks. `deploy/schedules.py --set` (and so
the app's Timetable tab) refuses one below 1.5 times a job's measured peak, because a
job killed for memory stops its model updating without saying why. After a change
that may make a job bigger, check the `resources` in its next events before lowering
anything. The retired models were never measured and keep 4 GB, more than the
recommended VM offers: measure one before enabling it, or Bacalhau leaves it queued.

## Sizing the VM

The VM's memory is what macOS loses while Colima runs, not what the jobs use: Colima's
`vz` VM takes memory from macOS as Linux touches it and does not give it back, and
Linux fills whatever is spare with page cache. So the VM's size, not Bacalhau's, is
what the Mac gives up. One job at a time needs 2 GiB (the largest job's 1 GB ceiling,
plus Docker and the kernel); two at once needed 3.

`macmini.sh setup` reads the VM's size and writes it into Bacalhau's launch agent,
warns if an enabled job could never fit, and says so if the VM is larger than the
jobs need. To shrink it to 2 GiB, when `macmini.sh status` shows no job
running:

```sh
deploy/home-compute/macmini.sh stop      # the scheduler and Bacalhau
export COLIMA_HOME=../home-compute-vm      # beside the checkout
colima stop -p home-compute
colima start -p home-compute --cpu 2 --memory 2   # kept in home-compute-vm/home-compute/colima.yaml
deploy/home-compute/macmini.sh setup     # rebuilds the image; Bacalhau gets 1 CPU, 1.5Gb
deploy/home-compute/macmini.sh start
deploy/home-compute/macmini.sh status    # Bacalhau's node should list 1 CPU and 1.5 GB
```

The login agent starts the same profile, so it comes back at 2 GiB after a reboot.
The VM keeps two CPUs for the image build; Bacalhau still runs one job at a time.
To give Bacalhau a different share of the VM, set `BACALHAU_CPUS` and `BACALHAU_MEMORY` (e.g.
`2Gb`) when running `setup`.

## Keeping the jobs in the background

Every job asks for one CPU, which Bacalhau hands to Docker as the container's CPU
limit, and only one job runs at a time: whatever runs, the jobs never use more than
one of the Mac's ten cores. They rarely use one: no job spends more than 25 CPU seconds a run,
and most of a run is spent waiting on a download or an upload.

`nice` inside the container would only order processes within the VM; macOS
schedules the VM's virtual CPUs as one ordinary app, so it is not used. To lower that
app's priority below your own, after each `colima start`:

```sh
renice -n 10 -p "$(pgrep -f com.apple.Virtualization.VirtualMachine)"   # undone by restarting Colima
```

That matches any `vz` VM, which is why `macmini.sh` does not do it for you. macOS's
background policy (`taskpolicy -b -p PID`) would go further, onto the efficiency cores
with throttled disk and network I/O, at the cost of HARMONIE's 785 MB download and its
upload taking noticeably longer.
